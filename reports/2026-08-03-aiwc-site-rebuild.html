Work summary · 3 August 2026

Rebuilding aiwc.org.au as a static, editable, story-shaped site

Moving the Australia India Water Centre from a WordPress/Elementor site — mirrored once into a Next.js app — onto the same architecture the MARVI site runs on, with a new art direction aimed at institutions and researchers.

01 — The problem

What was actually wrong

The symptom

aiwc.org.au is a WordPress/Elementor site. It holds genuinely strong material — a five-year bilateral partnership, 33 institutions, 108 researchers, a groundwater programme that has reached more than 10,000 villages — but presents it as a menu. A visiting research director has to open six pages and infer the case themselves.

The marvi-groundwater/aiwc repository already held one attempt at fixing this: a Next.js app plus a 55 MB docs/ folder containing a page-for-page static scrape of the WordPress site. GitHub Pages was configured but had never successfully built (status: null).

The underlying cause

Two distinct things, and it is worth separating them because only one is a "bug":

  • Editorially — the site's information architecture mirrored its org chart, not a reader's question. Nothing was broken; it just never made an argument.
  • Structurally — the previous attempt mirrored the output of WordPress rather than extracting the content. A scraped docs/ tree cannot be edited by AIWC staff, cannot be restructured, and re-scraping is the only way to update it.
Stated honestly: the Pages build failure was never diagnosed. It stopped mattering once the workflow was replaced wholesale, so the original cause is unproven. If it was an infrastructure problem rather than a workflow problem, it could recur — the first deploy from main is the test.

03 — How it was done

The real path, including what was eliminated

Hypotheses tested and eliminated

“Scrape the rendered HTML” — rejected before starting

The previous attempt did this. WordPress exposes a REST API at /wp-json/wp/v2/; it returned all 22 pages, 140 posts, 46 categories and 246 media records as structured data. Scraping would have inherited Elementor's div soup as the permanent content model.

“Person profiles are a label/value table” — half true, and the half that was false cost 90 emails

The profiles are tables, so a row-by-row label → value walk looked right and produced plausible output. But the contact row uses rowspan="3", which means the email and phone rows have only one <td> and no label of their own. The walk skipped them.

This produced no error. It produced 108 complete-looking profiles with 18 emails. It was only caught because the normaliser prints missing email: 90/108 — a completeness count, not an assertion.

The fix is two passes over the same table: structured rows for labelled fields, then a sweep for anything identifiable by shape — mailto:, orcid.org, a phone-like digit run. Result: 105 of 108.

“Read direct children for paragraphs” — worked for 21 of 22 articles

Elementor nests content arbitrarily deep. One article (WATER TALKS 2025, 6,244 characters) put every paragraph four containers down and came back completely empty. Again no error — the News page just rendered 190 words instead of 570. Caught by diffing parsed character counts against the raw text extraction, per article.

“The scroll-reveal animation is a nice touch” — nearly shipped a blank site

.reveal { opacity: 0 } with JS adding .in means that if app.mjs fails to load, every section below the hero is invisible. Now gated on a .js class set by an inline script before first paint; without scripting the content is simply visible. This also forced a build change — the build stripped all <script> tags and had to be narrowed to script[src].

“Verify by screenshot” — abandoned mid-task

The browser tool returned stale frames after programmatic scrolls: the DOM reported correct dark backgrounds and revealed content while the screenshot showed blank cream. Roughly an hour went into fighting this before switching to loading the built HTML into linkedom and driving the real controls. That test now runs in CI in about 200 ms. Screenshots were kept only for genuine art-direction judgement, on fresh page loads.

07 — The mathematical lens

The same event, read as structure

Everything above stands on its own. This layer re-reads the same work as mathematics — not to decorate it, but to name what was actually present.

Formulation A — a lossy map, and the cost of not being able to invert it

Let W be the source content, C the extracted JSON, S the built site. The pipeline is a composition:

S = r(e(W)), where e: W → C (extraction) and r: C → S (rendering)

r is total and deterministic — every element of C renders, and rebuilding from the same C gives byte-identical S. That is why the CMS preview cannot drift: preview and publish are the same r.

e is the dangerous one, because it is not injective and silently so. Distinct source documents mapped to the same impoverished record. The two bugs are exactly two collapses:

rowspan bug: e(profile_with_email) = e(profile_without_email) — 90 of 108 collapsed nesting bug: e(nested_article) = e(empty_article) — 1 of 22 collapsed

What makes this interesting rather than trivial: you cannot detect a non-injective map by examining its output. Both outputs were well-formed. Detection required a second, independent map e′ (the plain-text extractor) and comparing a cheap invariant — character count — across both:

flag article a ⟺ |e(a)| < ½·|e′(a)| and |e′(a)| > 500

This caught exactly one article: 0 characters against 6,244. The email bug used the same idea with a different invariant, counting non-null fields rather than comparing two maps. Interpretation: the assurance came not from checking correctness but from checking agreement between two independent derivations, which is a much weaker and much cheaper thing to arrange.

Formulation B — the site as a directed graph, and verification as reachability

Let G = (V, E) where V is the 156 built documents and E the 3,161 internal links. verify.mjs asserts closure — no edge leaves the vertex set:

∀ (u,v) ∈ E : v ∈ V (0 violations)

Reading the two designs as graphs makes the people decision precise. In the rejected inline design, all 108 profiles live on one vertex, so d(home, any researcher) = 2 but the researcher is not addressable — no vertex denotes them, so nothing external can cite them. In the built design, each researcher is a vertex: d = 2 still, and now |V| grows by 108 while the citable set grows from 15 to 156. The cost of the extra vertices is 141 files; the gain is that an external citation can point at a person.

The rail navigation makes G have diameter ≤ 3 from any page — every page links every other top-level page, so the graph is nearly complete on the 15 nav vertices, with profile vertices hanging at distance 1 from their directory.

What each formulation assumes, and hides

A — the map view

Reveals: that silent data loss is a statement about injectivity, and that the defence is redundant derivation rather than inspection.

Assumes: that "content" is a set with a meaningful equality — which is false at the edges. Is a reordered paragraph list the same content? A is silent on the editorial restructuring, which is the part a reader would call the actual work.

B — the graph view

Reveals: that addressability is a property of the vertex set, not the edge set, and that this is exactly what the old site lacked.

Assumes: links are homogeneous and unweighted. It cannot see that the home page's ordering carries an argument — to B, a rearranged home page is the same graph.

Neither sees the thing the brief actually asked for. The narrative ordering is a total order on a sequence of assertions chosen to be persuasive — closer to rhetoric than to either structure. That both formulations are blind to it is itself the honest finding: the mathematics here describes the plumbing well and the editorial judgement not at all.

One claim, left open

For the practice folder. The nesting bug was caught by a two-map agreement test with threshold ½. Formalise: let e, e′ be two extractors, and suppose e collapses a document to a strictly smaller record with probability p, independently per document, while e′ does so with probability q, and that their failures are independent. A threshold test flags document a when |e(a)| < θ·|e′(a)|.

Question: for n documents, what is the probability that at least one collapse goes undetected, as a function of θ, p, q, and the distribution of document sizes? Then: is there a θ minimising expected total error (missed collapses plus false alarms), and does it depend on the size distribution — or, as the ½ here quietly assumes, not at all?

Real numbers to anchor it: of 22 articles, 12 exceed the 500-character floor the test applies. Exactly one collapsed — 0 characters against 6,244, a ratio of 0.000. The other 11 had |e|/|e′| ratios of 0.905, 0.977, 0.980, 0.991, 0.992, 0.993, 0.996, 0.997, 0.997, 0.998, 0.998. Zero false alarms at θ = ½, and θ anywhere in (0.01, 0.90) would have worked on this sample. The question is whether that enormous gap is a property of the failure mode — container nesting fails all-or-nothing, never partially — or luck. If it is structural, θ barely matters and the test is far more robust than it looks; if the 0.905 is near a real tail, it matters a great deal.
