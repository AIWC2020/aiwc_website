The CMS that looked like it had no photo upload

3 August 2026 · AIWC2020/aiwc_website · fix shipped as 908124e
Symptom reported: “why cms has no upload photos like decap?”

1What was the problem

The Sveltia CMS at /aiwc_website/admin/ appeared to be missing image upload entirely. Compared against Decap — which shows a text-labelled Media button — there was nothing recognisable to click.

The upload button was there the whole time. It was painting its own name.

The actual cause, proven

Material Symbols is a ligature font. The CMS's icon markup genuinely reads <span class="material-symbols-outlined">photo</span>, and the font's 'liga' feature is what substitutes a picture for the letters. The admin page's Content-Security-Policy allows font-src 'self' data: only, so the three fonts the CMS fetches from cdn.jsdelivr.net were all blocked — and every icon fell back to rendering its own name as text.

The policy's own comment in admin/index.html had anticipated this and priced it wrongly: it said blocking the third-party calls “costs fallback fonts and no banner, nothing more.” For the two text fonts that was true. For the icon font it cost the discoverability of the media library.

2What is the solution

All three fonts are now served from the repository, so they satisfy font-src 'self' and the policy stays exactly as strict as it was.

The @font-face descriptors — font-weight, unicode-range, font-display, size-adjust: 110% — are copied verbatim from the bundle, with only src changed. Rendering is therefore identical to the upstream CDN build rather than merely similar. Paths are relative, so they survive the base path changing from /aiwc_website to a domain root if a CNAME is ever added.

3How I did it — including what was wrong

Four hypotheses were tested and eliminated. Three of them were mine, and two of those were confidently wrong, which is the useful part of this record.

  1. “The chatroom is in this repo.” eliminated
    The session began in the MARVI repo hunting a missing “chatroom”. Nothing matched in the tree or in history. Wrong repository entirely.
  2. “The chatroom was the chat-guided editing flow.” eliminated
    Found a real AGENTS.md + issue-form setup on marvi-groundwater/aiwc, removed by a rebuild. Presented it confidently. The user corrected me: wrong site. The real site was aiwc2020.github.io/aiwc_website/, where the thing that had actually vanished was /editor/ — added 14:52 and deleted 19:26 the same day.
  3. “The CMS has no upload configured.” eliminated
    Disproved by evidence, not opinion: the deployed config.yml declares 5 image widgets, media_folder points at assets/photos, and that folder already holds 90 images.
  4. “The icon font is blocked.” confirmed
    document.fonts reported Material Symbols Outlined: error and Source Sans 3: error. The console was completely empty — font failures are a FontFaceSet state change, not a logged exception. The DOM's aria-label="Assets" proved the button existed while the pixels said otherwise.
  5. “A stylesheet in <head> will lose to the bundle's rules.” eliminated by measurement
    I expected to have to patch the vendored bundle, reasoning that the bundle injects its @font-face rules at mount — therefore last — and that the last matching rule wins. Measured instead of assumed, and it was false. A face that fails to load is skipped in favour of one that loaded. The simple <link> works.
trap

Two APIs lie about this fix. document.fonts.check() still returns false and document.fonts.load() still rejects with a network error, because both inspect every matching face — including the broken CDN ones, which remain declared. Neither is evidence of a problem. The only trustworthy signal was measuring the rendered width: 55 px (word) versus 24 px (glyph).

One self-inflicted detour worth recording: extracting files with $B:AGENTS.md in zsh silently produced a 0-byte file, because :A is zsh's absolute-path expansion modifier. The shell redirect created the output file before git failed, so the file listing looked correct — only the size column gave it away.

4Why this beats the alternatives

OptionVerdictReasoning
Vendor the fonts, re-declare locally chosen Policy untouched. Vendored bundle untouched, so the documented upgrade path — drop in a new file, change one line — still works. Descriptors copied verbatim, so rendering is identical.
Patch the vendored bundle's URLs rejected Certain to work, but silently breaks the upgrade path: every future version bump would need re-patching, and nothing in the repo would say so.
Add cdn.jsdelivr.net to font-src rejected One line, but reopens a third-party dependency on a page that deliberately has none. The admin page holds a GitHub token in localStorage, and both published Sveltia advisories are stored XSS — the strictness is load-bearing.
Inject @font-face after mount via script rejected Was the planned fallback if ordering mattered. Measurement showed it doesn't, so this only adds a race condition.
Subset the icon font to the glyphs used better long-term Not done, and it is the honest improvement. 748 KB carries the whole Latin range for perhaps 20 icons; a subset would be a few KB. It needs a build step and a glyph inventory, and the CMS's icon set is chosen at runtime — so doing it safely means enumerating icons from the bundle, not guessing.

7The mathematical lens

The structure genuinely present here is small but real: a diagnosis (choosing among candidate causes under uncertainty) followed by a selection rule (which of several competing declarations a browser actually obeys). Those are different kinds of object, and reading the event through each reveals a different half of what happened.

Formulation A — elimination over a hypothesis space

Treat the diagnosis as a hypothesis set H with observations that zero out members. Real counts from this session: |H| = 4 candidate explanations for “no upload button”, reduced to 1 by three observations.

H = { wrong-repo, wrong-site, not-configured, font-blocked }
e₁ : config declares 5 image widgets ⟹ P(not-configured) = 0
e₂ : assets/photos contains 90 files ⟹ reinforces ¬not-configured
e₃ : aria-label "Assets" exists in the DOM ⟹ button exists ⟹ rendering fault
e₄ : document.fonts → 2 faces in state "error"

What it reveals: the informative observations were the ones capable of eliminating, not confirming. e₃ did the most work — a single DOM attribute separated “feature absent” from “feature invisible”, collapsing the space in one step. What it assumes: that the hypotheses are mutually exclusive and that I enumerated the right ones. Both failed early — my first two hypotheses were not in the true space at all, which is why the user's correction, not any evidence I gathered, was what advanced the diagnosis.

Formulation B — a choice function over a partially ordered set of faces

Let F be the @font-face rules matching one family, ≺ the declaration order (a total order here), and L ⊆ F the subset that loaded successfully. In this event |F| = 2 per family across 3 families, so 6 faces, with |L| = 2.

predicted rule: σ(F) = max≺(F) → CDN face → load error → fallback to system text
observed rule: σ(F) = max≺(F ∩ L) → local face → ligature glyph

consequence: the two rules disagree exactly when max≺(F) ∉ L

What it reveals: my entire plan to patch the vendored bundle rested on assuming the first rule. The distinction is one intersection, and it decided whether the fix was three new files or a modified third-party dependency. What it assumes: that ≺ is total and that “matching” is a clean predicate — neither is quite true once unicode-range partitions the codepoint space, which is precisely where the claim below bites.

What each is for

A is about search — it prices information and tells you which probe to run next; it says nothing about what the browser will do. B is about semantics — it predicts behaviour exactly, and it is where my reasoning actually broke. Notably, A cannot catch a B-type error: I could have run the elimination perfectly and still shipped the wrong fix, because the faulty belief was about the selection rule, not the cause. The measurement — 24 px against 55 px — is what tested B, and it was two lines of code.

For the practice folder

Let F be a set of @font-face declarations for one family, ordered by declaration under ≺, each carrying a unicode-range subset Uf ⊆ 𝒰, and let L ⊆ F be those that load. Define the per-codepoint choice σ(c) = max≺{ f ∈ F ∩ L : c ∈ Uf }.

Claim to settle: σ is monotone under augmentation — adding any face g with g ∈ L never makes the rendered result for any codepoint fall further down the family fallback chain than it was before.

State precisely the conditions on Ug and on g's weight/style descriptors under which this holds, and either prove it or construct a counterexample in which adding a face that does load makes some codepoint render worse. The size-adjust: 110% on Source Sans 3 is a hint that “worse” may need defining as something finer than “falls back”.
